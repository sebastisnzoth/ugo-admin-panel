# Stitch → UGO visual correspondence matrix

Auditoría documental de correspondencia entre exports físicos de Stitch versionados en `design/stitch/sources/` y la implementación actual en `src/mvp/`.

## Reglas de esta matriz

- No se copió `code.html` a `src/`.
- No se modificó la app ni componentes React.
- Los HTML/PNG son referencia visual, no código productivo.
- Claims no verificados a neutralizar antes de runtime: escrow, BACEN, custodia, CFT, SUSEP, AWS, forensic, biometric, póliza, satelital, seguro, fiduciario, certificación legal.
- Prioridad: Alta = impacta flujo principal o parity visual; Media = módulo existente con ajustes; Baja = referencia, asset, o alcance futuro/no productivo.

## Resumen ejecutivo

| Área | Fuente Stitch | Equivalencia UGO | Lectura |
| --- | --- | --- | --- |
| Cliente Web | `stitch_ugo_client_web_app` | `ClientApp`, `ClientQuantumExperience`, `UgoWeb`, módulos client | Buena cobertura funcional; falta parity visual granular por frame. |
| Cliente Mobile | `stitch_ugo_services_mobile_app` | `UgoWeb`, `ClientApp`, CSS responsive/mobile | Muchos estados especiales existen como referencia, varios son sobrediseñados/legalizados. |
| Provider | `stitch_ugo_provider_onboarding_app` | `ProviderApp`, onboarding, home, payout, evidencia | Flujo principal cubierto parcialmente; scanner IA y claims escrow requieren bloqueo. |
| Admin | `stitch_task_action_manager` | `AdminPhase2`, `AdminServicesPro`, `AdminDecisionCenter`, finanzas, users | Alta correspondencia por módulos; claims forenses/biométricos no deben copiarse. |
| Super Admin | `stitch_ugo_admin_platform_design` | `SuperAdminCommandCenter`, `AdminSystemSettings`, `AdminHomeStitch` | Base implementada; Stitch sirve para elevar layout/comando sin copiar HTML. |

## Hallazgos de auditoría

1. `src/mvp/` ya contiene una base amplia para cliente, proveedor, admin y superadmin; Stitch debe usarse como fuente visual, no como reemplazo directo.
2. La mayor brecha es visual/estructural: densidad de cards, jerarquía, navegación responsive, estados vacíos y overlays de mapa/servicio.
3. La mayor brecha de producto/legal está en claims: custodia/escrow, pólizas, certificaciones, biometría, peritaje/forense, fiduciario y sellos oficiales.
4. Varios frames de Stitch son documentos, diagramas o assets; no corresponden a pantallas productivas y deben permanecer en `design/stitch/sources/`.
5. La implementación futura debe partir de componentes React existentes y del design system UGO, portando tokens, layout y affordances visuales de forma incremental.

## Recomendación de fases futuras

1. Cliente: priorizar home/radar, solicitud, matching, tracking y cierre/calificación.
2. Provider: priorizar onboarding, oportunidades, detalle/presupuesto, navegación/llegada, evidencias y payout.
3. Admin/Super Admin: priorizar dashboard, servicios en vivo, proveedores/KYC básico, finanzas/retiros y command center.
4. Bloquear o reescribir todo claim no verificado antes de llevar cualquier copy al runtime.
