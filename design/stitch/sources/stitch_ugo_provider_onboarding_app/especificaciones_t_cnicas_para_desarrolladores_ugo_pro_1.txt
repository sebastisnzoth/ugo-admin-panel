# UGO Pro — Especificaciones Técnicas de Ingeniería y Guía de Implementación (Handoff)
**Versión:** 1.0 (Ready for Dev) • **Destinatarios:** Equipos de Frontend (Mobile / React Native / Flutter), Backend (APIs / Microservicios) & DevOps  
**Ecosistema:** UGO Pro Specialist Application • **Plataformas Objetivo:** iOS / Android • **Arquitectura:** Event-Driven / RESTful + WebSockets / Escrow Ledger

---

## 1. Arquitectura General y Stack Tecnológico Recomendado

```
[ Cliente Mobile (React Native / Flutter) ]
       │              ▲
       ▼ REST (TLS)   │ WebSockets (WSS - Telemetría, Chat & Radar)
┌────────────────────────────────────────────────────────┐
│               API Gateway (Reverse Proxy / Auth)       │
└───────────┬───────────────────┬────────────────────┬───┘
            │                   │                    │
            ▼                   ▼                    ▼
   [ Auth & Identity ]  [ Job & Escrow Engine ]  [ AI / Lens Vision ]
   • JWT + Biometrics   • Event Ledger           • Embedding & OCR
   • OTP (SMS Gateway)  • PIX / Bacen Direct     • Vector DB (Catalog)
```

- **Frontend Mobile:** React Native (TypeScript) o Flutter.
- **Backend Core:** Node.js / Go / Kotlin microservicios.
- **Bases de Datos:** PostgreSQL (transaccional ACID para órdenes y billetera), Redis (caché de radar y sockets), S3 Compatible Object Storage (evidencias fotográficas cifradas).
- **Seguridad & Hash:** Hashing SHA-256 de imágenes en cliente y servidor para inmutabilidad legal de pruebas.

## 3. Modelo de Entidades y Estados de Orden (Lifecycle)

```
[ DRAFT ] ──> [ QUOTED ] ──> [ ESCROW_LOCKED ] ──> [ IN_ROUTE ] ──> [ CHECKED_IN (OTP) ]
                                                                             │
[ COMPLETED ] <── [ CLIENT_APPROVED ] <── [ REVIEW_PENDING ] <── [ IN_PROGRESS ]
      │                                                                      │
      ▼                                                                      ▼
[ PIX_DISBURSED ]                                                      [ IN_DISPUTE ]
```

### Tabla `JobOrder` (Esquema SQL)

```sql
CREATE TABLE job_orders (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    order_number VARCHAR(16) UNIQUE NOT NULL, -- e.g. #8492
    specialist_id UUID NOT NULL REFERENCES specialists(id),
    client_id UUID NOT NULL REFERENCES clients(id),
    status VARCHAR(32) NOT NULL, -- DRAFT, QUOTED, ESCROW_LOCKED, IN_PROGRESS, COMPLETED, DISPUTED
    category VARCHAR(64) NOT NULL, -- "Plomería", "Electricidad"
    initial_amount DECIMAL(10, 2) NOT NULL,
    addon_amount DECIMAL(10, 2) DEFAULT 0.00,
    platform_fee_percent DECIMAL(5, 2) DEFAULT 15.00,
    escrow_status VARCHAR(32) NOT NULL, -- PENDING_DEPOSIT, HELD_IN_ESCROW, RELEASED, REFUNDED
    otp_start_code VARCHAR(6),
    otp_validated_at TIMESTAMP WITH TIME ZONE,
    sha256_before_photo VARCHAR(64),
    sha256_after_photo VARCHAR(64),
    pressure_bar_test DECIMAL(4, 2),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
```

## 5. WebSockets & Protocolo de Eventos en Tiempo Real

Para el Radar de trabajos, Telemetría en Ruta (GPS) y Chat de soporte tripartito, se establece conexión a:  
`wss://stream.ugopro.com/v1/ws?token=<JWT>`

| Evento WS | Dirección | Descripción / Payload |
| :--- | :--- | :--- |
| `order:job_alert` | Server ➔ Client | Notificación push de nuevo trabajo en radar con timer de 120s. |
| `specialist:geo_tick` | Client ➔ Server | Emisión periódica cada 10s de lat/lng durante navegación en ruta. |
| `escrow:funded` | Server ➔ Client | Alerta de depósito en garantía confirmado (R$ 250,00 retenido). |
| `chat:message` | Bidireccional | Mensaje de texto/audio con flag `is_adendum_proposal`. |
| `dispute:mediator_note` | Server ➔ Client | Actualización de dictamen técnico por el perito asignado. |

## 6. Consideraciones de Seguridad y Cumplimiento

1. **LGPD & CPF Hashing:** Los números de CPF y cuentas bancarias siempre deben almacenarse cifrados en base de datos (`AES-256-GCM`) y transmitirse mascarados en interfaces públicas.
2. **Firmas de Evidencias:** Cada fotografía capturada por el módulo nativo calcula su hash SHA-256 antes de la subida para garantizar que no fue manipulada externamente.
3. **Idempotencia en Pagos:** Todas las peticiones al motor Escrow y retiro PIX deben requerir un encabezado `Idempotency-Key: <UUID>` único para prevenir cobros o transferencias duplicadas en caso de inestabilidad de red 4G/5G.
