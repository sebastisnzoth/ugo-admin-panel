## 2. P0 ya cerrados que NO deben reabrirse sin evidencia

### 2.1 Aceptación atómica de oportunidades
La aceptación se serializa server-side y evita doble asignación. Cliente UI no es autoridad.

### 2.2 Pago efectivo first-class
El efectivo es una forma de pago explícita, presencial y auditable. No se representa como custodia electrónica.

### 2.3 Evidencia previa por draft
La evidencia de solicitud se vincula a un draft concreto y no a una ventana temporal ambigua.

### 2.4 Evidencia operacional por lifecycle
- `Antes` en `llegado`;
- `Durante/Después` en `en_progreso`;
- evidencia final requerida para pedir revisión.

### 2.5 Llegada
Backend conserva autoridad y radio operativo vigente de 200 m cuando aplica coordenada exacta.

### 2.6 Ampliaciones con dinero
El trabajo adicional no puede convertirse en alcance financiado ficticiamente. El delta electrónico activo se reconcilia antes de quedar incorporado.

## 4. P0 abiertos reales

### P0-A · E2E Cliente ↔ Proveedor ↔ Backend
**Problema:** los contract tests prueban invariantes sobre código/migraciones, pero no ejecutan el journey completo con dos sesiones y base aislada.

**Cierre requerido:**

```text
Cliente crea solicitud
→ matching
→ Proveedor acepta
→ forma de pago válida
→ en_camino
→ llegada
→ evidencia Antes
→ iniciar
→ ampliación opcional
→ evidencia Después
→ revisión
→ Cliente aprueba o disputa
→ cierre financiero
```

Probar electrónico y efectivo por separado.

### P0-B · RPC/RLS real contra base aislada
**Problema:** `npm test` actual es un gate contractual estático; no sustituye ejecución real de RLS/RPC.

**Cierre requerido:** actor permitido + actor denegado para servicios, ofertas, pagos, evidencias, ampliaciones y disputas.

### P0-C · Concurrencia/idempotencia de dinero
Ejecutar contra DB aislada:
- doble aceptación;
- doble webhook;
- retry de ampliación;
- webhook duplicado de delta;
- reembolso posterior de delta;
- doble confirmación de efectivo;
- doble aprobación/cierre.

### P0-D · Convergencia Realtime
Probar que Cliente y Proveedor convergen después de:
- transición de servicio;
- pago;
- evidencia;
- ampliación;
- reconexión;
- evento duplicado.

No aceptar estado local como segunda verdad.

## 8. Regla de ejecución desde este punto

Orden obligatorio:

```text
1 cerrar P0 contractual ejecutable
2 ejecutar CI
3 corregir fallo real
4 validar nuevamente
5 sincronizar maestros/Roadmap
6 pasar al siguiente P0
```

No declarar el journey `VALIDATED` hasta tener evidencia real de RPC/RLS/E2E apropiada.

## 9. Próximo bloque automático

**Implementar el harness de integración para RPC/RLS Cliente ↔ Proveedor sobre una base de pruebas/entorno seguro**, empezando por:

1. aceptación única;
2. gate de pago para `asignado → en_camino`;
3. evidencia Antes para `llegado → en_progreso`;
4. evidencia Después para `en_progreso → esperando_aprobacion`;
5. aprobación Cliente con ownership;
6. efectivo confirmado;
7. ampliación con delta financiado.

Si el entorno de CI no dispone todavía de credenciales/base aislada, el harness debe quedar preparado y el bloqueo documentado sin usar producción como entorno de prueba.

---

## 10. Criterio de éxito

El P0 Cliente ↔ Proveedor queda cerrado cuando:

- ambos roles usan el mismo `serviceId`;
- las transiciones sólo ocurren por autoridad backend;
- dinero y evidencia bloquean estados inválidos;
- concurrencia no duplica asignaciones/cobros;
- Realtime converge al mismo estado persistido;
- errores/retry no corrompen el servicio;
- pruebas positivas y negativas son reproducibles;
- Core CI queda verde;
- maestros y Roadmap reflejan ese estado real.
